# renderpulse

**renderpulse** keeps [Render](https://render.com) free-tier web services awake by sending realistic, randomized HTTP requests well inside Render's 15-minute spin-down window.

Render spins down a Free web service that goes **15 minutes without inbound traffic** ([docs](https://render.com/docs/free)). renderpulse visits each service on an independent, randomized schedule (default every **3–7 minutes**) so the idle timer never expires — and it does so looking like ordinary browser/API traffic, not a metronome.

## What it does

- **Per-service independent loops** — every service gets its own schedule; nothing fires in lockstep.
- **Randomized intervals** — uniform over `--interval-min`..`--interval-max` (default 3–7 min, safely under 15).
- **Genuine-looking requests** — real browser profiles (Chrome/Firefox/Safari, desktop+mobile) with internally consistent headers: matching `User-Agent` + `sec-ch-ua` + `sec-fetch-*`, plausible `Referer`/`Accept-Language`, cache-busting query params.
- **Real routes** — weighted route pools built from live-probed endpoints of the tomato fleet (auth/realtime/restaurant/utils/rider/admin), including the socket.io polling handshake and plausible 404s a browser would produce anyway. Every response — even a 404 — is generated by the app itself and resets the idle timer. `/robots.txt` is deliberately never requested: Render answers it at the edge while a service is spun down, so it would NOT wake the service.
- **Session bursts** — a visit is 1–3 related requests with human-scale pauses, like a person clicking through a page.
- **Per-machine randomness** — the RNG is seeded from `/etc/machine-id` (or `--seed`), so two hosts never produce the same schedule. Startup is additionally jittered (default up to 45 s).
- **Sharding** — `--shard i/n` splits the fleet round-robin so two machines can cover disjoint sets of services with zero duplicate traffic.
- **Cold-start tolerant** — 90 s request timeout (Render takes ~1 min to spin a service back up), with a few quick retries when a host is unreachable.
- **Ops-friendly** — `--once`, `--dry-run`, `--log-file` with size-based rotation, `--log-json`, graceful SIGTERM shutdown. Single static binary, zero runtime dependencies.

## Install

Prebuilt static binaries for **Linux / macOS / Windows × amd64 / arm64** are attached to every [release](../../releases). This repo is private, so downloads need `gh` (logged in) or a token.

### One-liner (Linux/macOS, with gh installed)

```bash
gh repo clone pentoshi007/renderpulse   # only needed for install.sh
cd renderpulse && sudo bash install.sh
```

`install.sh` detects your OS/arch, downloads the matching release asset with `gh` (or `curl` + `GITHUB_TOKEN`), verifies the SHA-256 checksum, and installs to `/usr/local/bin/renderpulse`.

### Manual

```bash
# with gh
gh release download v0.1.0 --repo pentoshi007/renderpulse --pattern '*linux_arm64*'
tar xzf renderpulse_0.1.0_linux_arm64.tar.gz
sudo install renderpulse_0.1.0_linux_arm64/renderpulse /usr/local/bin/

# or with a token
curl -fL -H "Authorization: Bearer $GITHUB_TOKEN" \
  -o renderpulse.tar.gz \
  "https://github.com/pentoshi007/renderpulse/releases/download/v0.1.0/renderpulse_0.1.0_linux_arm64.tar.gz"
```

Windows: download `renderpulse_<ver>_windows_amd64.zip`, extract, run `renderpulse.exe` from PowerShell/cmd.

### From source
```bash
git clone https://github.com/pentoshi007/renderpulse
cd renderpulse && go build -o renderpulse .
```

## Usage

```bash
renderpulse [flags]
```

| Flag | Default | Meaning |
|---|---|---|
| `--interval-min` | `3m` | min delay between visits to the same service |
| `--interval-max` | `7m` | max delay (rejected if ≥ 14m — no safety margin under the 15-min spin-down) |
| `--timeout` | `90s` | per-request timeout; covers Render cold starts |
| `--startup-jitter` | `45s` | random delay before the first visit, spreading instances apart |
| `--think-min/max` | `800ms`/`6s` | pause between requests inside one browsing session |
| `--shard` | `1/1` | only handle services `i/n` (e.g. `1/2` on machine one, `2/2` on machine two) |
| `--once` | off | visit every assigned service once, then exit |
| `--dry-run` | off | log requests without sending them |
| `--log-file` | stdout | append logs here, rotate at `--log-max-mb` (keeps one `.1` generation) |
| `--log-json` | off | JSON log lines |
| `--seed` | machine-id | override the randomness seed |
| `--list-services` | — | print the fleet and shard assignment, then exit |
| `--version` | — | print version |

Try it safely first:

```bash
renderpulse --dry-run --once
renderpulse --once --log-json
```

## Run forever on two Oracle Linux machines

You have two options. **Both are safe against synchronized traffic** — schedules are seeded from each machine's `/etc/machine-id` and every loop is independently randomized, so two instances never align. Sharding additionally guarantees zero duplicate traffic per service.

### Option A — systemd (recommended)

```bash
sudo cp deploy/renderpulse.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now renderpulse
journalctl -u renderpulse -f
```

Split the fleet across the two machines by editing the `ExecStart` line:

- machine 1: `ExecStart=/usr/local/bin/renderpulse --shard 1/2`
- machine 2: `ExecStart=/usr/local/bin/renderpulse --shard 2/2`

Or run the full fleet on both (each machine keeps every service awake on its own independent schedule) — just leave `--shard 1/1`.

### Option B — tmux

```bash
tmux new -s renderpulse
renderpulse --log-file ~/renderpulse.log
tmux detach    # Ctrl-b d
# reattach later:  tmux attach -t renderpulse
```

To survive reboots without systemd, add to `crontab -e`:

```cron
@reboot tmux new -d -s renderpulse 'renderpulse --log-file ~/renderpulse.log'
```

## Logs

Plain text by default:

```
time=2026-09-09T15:40:07+05:30 level=INFO msg="request sent" service=admin method=GET path=/api/v1/users status=401 bytes=45 elapsed=80ms profile=chrome-android
time=2026-09-09T15:40:09+05:30 level=INFO msg="next visit scheduled" service=admin in=6m28s
```

Any HTTP status (200/401/404…) counts as a successful keep-alive — the app itself answered. `request failed` lines mean the host was unreachable; renderpulse retries a few times quickly, then continues on schedule.

## Fair use — read this before running 24/7

- Render grants each workspace **750 free instance-hours per month**. A free service consumes hours only while *running*; 6 services kept awake 24/7 burn ~4320 hours, exhausting the budget in about **5 days**, after which Render suspends all free web services until the next month ([docs](https://render.com/docs/free#free-instance-hours)). If you need all six always-on, budget for a paid instance on some of them, or let renderpulse run only during hours you actually use the stack (e.g. a systemd timer window).
- Keep-alive pingers are a common workaround, but Render's free tier is intended for hobby projects and the docs ask you not to treat it as production. Keep intervals reasonable (the defaults are deliberately modest) and expect Render to change free-tier behavior at any time.
